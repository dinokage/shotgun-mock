# RBAC, Departments, and Admin Panel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the disconnected 9-role permission scheme with a real 6-role model (admin/production_head/producer/lead/artist/client), add real department data with a real user↔department link, and give Admin genuine user/role/department management plus a cross-department monitoring dashboard.

**Architecture:** New `departments` table + `usersTable.departmentId` column back a new `GET /api/departments` and an extended `POST/PATCH /api/users` API. The frontend's already-built 14-capability system (`store/permissions.ts`, wired into `Sidebar.tsx`/`App.tsx` today) is *reused as-is* — only the role list and each role's capability set change — which keeps this change surgical instead of a rewrite. A new `/admin` page composes existing patterns (a data table, a create/edit dialog) into the user-management + cross-department view.

**Tech Stack:** Express 5 + Drizzle ORM + Postgres (backend), React + Vite + Zustand + wouter (frontend), Playwright for verification (no unit test framework exists in this repo for either side — see Global Constraints).

**Spec:** `docs/superpowers/specs/2026-08-26-rbac-admin-panel-design.md`

## Global Constraints

- `pnpm run typecheck` must stay at zero errors across the whole workspace after every task — this is the project's real, working correctness gate (confirmed repeatedly today; there is no unit test suite for either the backend or the frontend that runs in CI).
- Tenant isolation is load-bearing everywhere: every new/changed query must be scoped by `tenantId`, following the exact pattern already used in `artifacts/api-server/src/routes/projects.ts` (`eq(table.tenantId, tenantId)`), never trust a client-supplied tenant value.
- **Deviation from the spec, discovered while reading the real files (documented, not silent):** the spec's §3 proposed a fresh 15-capability list. The actual codebase already has a working, well-integrated 14-capability system (`CAPABILITY_IDS` in `artifacts/forge/src/store/permissions.ts`) wired into `Sidebar.tsx`'s nav gating and multiple pages. Inventing new capability strings would mean re-touching every one of those call sites for no functional gain. This plan reuses the existing 14 capability IDs verbatim and only changes which *roles* exist and which capabilities each holds. Department-scoping (who sees only their own department) is handled as a *separate* dimension via `currentUser.departmentId`, not via new capability strings — matching how `store/permissions.ts` already separates `STUDIO_LEADERSHIP_ROLES` from `DEPARTMENT_LEADERSHIP_ROLES`.
- Reuse `manage_members` as the "create/reassign users" capability (its existing label — "Invite, remove, or edit studio members" — already matches; no need for the spec's proposed `manage_users`).
- The final 6-role list is exactly: `admin`, `production_head`, `producer`, `lead`, `artist`, `client`. `production_head` is new; `producer` already exists as a `Role` union member (currently unused/orphaned in the codebase) and is being given real meaning; `vfx_producer`, `production_manager`, `coordinator`, `supervisor`, `senior_artist`, `junior_artist` are retired.
- No new dependencies.
- Do not touch `artifacts/mockup-sandbox`.
- Migrations must be generated and committed (not left to regenerate at build time) — follow the exact process used today: `DATABASE_URL=<any value> pnpm --filter "@workspace/db" run generate` (works now that the Windows path bug in `drizzle.config.ts` is fixed), then `git add lib/db/drizzle`.

      .select()
      .from(usersTable)

    if (!existing) return res.status(404).json({ error: "Not found" });

        .select()
        .from(tenantRolesTable)
        .where(and(eq(tenantRolesTable.id, roleId), eq(tenantRolesTable.tenantId, tenantId)));

        const [dept] = await db
          .select()
          .from(departmentsTable)
          .where(and(eq(departmentsTable.id, departmentId), eq(departmentsTable.tenantId, tenantId)));
        if (!dept) return res.status(400).json({ error: "Invalid departmentId" });
      }
      updates.departmentId = departmentId;
    }

    if (Object.keys(updates).length === 0) {
      return res.status(400).json({ error: "No valid fields to update" });
    }

    await db.update(usersTable).set(updates).where(eq(usersTable.id, userId));

    const [updated] = await db
      .select()
      .from(usersTable)
      .where(eq(usersTable.id, userId));
    const { hashedPassword: _omit, ...user } = updated;
    return res.json(user);
  } catch (err) {
    req.log.error(err, "Failed to update user");
    return res.status(500).json({ error: "Internal server error" });

    </div>
  );
}
