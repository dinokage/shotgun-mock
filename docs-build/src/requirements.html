1  Executive summary

Forge is a production tracking and review platform built for Symbiosys Technologies' animation and VFX operation, replacing spreadsheet-based shot tracking and ad-hoc review with a single system of record.

1.1 The problem

Production tracking ran on spreadsheets maintained per show. Shot status was accurate only as of the last manual update, review feedback arrived through chat and email where it was frequently lost, and approvals left no record of who signed off on what. Commercial alternatives were evaluated and rejected on cost, on their cloud-hosted delivery model, and on the pipeline work required to adapt them to the studio's existing episodic tracksheet format.

1.2 The solution

A self-hosted web platform covering the full production path: import of existing tracksheets, hierarchical tracking from project through episode, sequence and shot to individual task, role-scoped task assignment, a frame-accurate review player with annotation, a multi-stage approval chain, external client review by access link, and attendance and effort recording.

1.3 Current status

The system is deployed and in production use. At the time of writing it holds 1,065 shots and 1,066 tasks imported from live production tracksheets, across 65 user accounts spanning six roles. This document therefore records requirements for a system that largely exists — it is both a specification and a record of what was built, and each requirement carries a delivery status.

2  Business background and problem statement

2.1 Operating context

Symbiosys Technologies produces animation and visual effects work, principally episodic content organised into episodes, sequences and shots. Work passes through departmental stages, each contributing to a shot before it advances. A single episode commonly contains several hundred shots, each requiring individual tracking, review and sign-off.

On the administrator constraint

The administrator role holds no task or review capability. This follows from BR-011: the person who administers accounts and monitors the studio should not also be a participant in the production approval chain, so that oversight remains independent of the work being overseen. The constraint is enforced server-side by capability grant, not by hiding controls in the interface.

10.2 Decision records

DEC-001  ·  TypeScript end to end

Decision. A single language across frontend, API and shared packages, with types shared through workspace packages rather than duplicated.

Rejected. A Python or Go API tier, which would have required the request and response contract to be defined twice and kept in step by discipline alone.

Criteria. Contract safety across the network boundary; team size; the cost of a type mismatch reaching production.

Consequence accepted. Node's runtime characteristics for CPU-bound work are inferior to Go's. Accepted because the workload is I/O-bound: database reads, file serving and JSON.

DEC-002  ·  Prisma as the ORM, replacing Drizzle

Decision. Prisma Client is the sole database access layer. The system was originally built on Drizzle ORM and migrated in full.

What the migration actually involved. Twenty-six tables declared across eight schema files, a custom migration runner, and query-builder calls in seventeen of twenty route files plus two library modules and three operational scripts. The work was planned as eleven sequenced tasks, executed against a clone restored from real production data, and cut over in a single planned downtime window rather than a gradual dual-write rollout.

Honest statement of the driver. The migration was undertaken on a directive to standardise on Prisma. It was not the outcome of a comparative trade-off study, and this document does not present one retrospectively.

Supporting technical justification. A single declarative schema file replaces eight hand-maintained definition modules; the generated client provides types derived from the schema rather than asserted alongside it; first-party migration tooling offers a deploy command suited to running unattended at container start, which is how migrations are applied here; and the larger installed base widens the pool of engineers who can maintain the system.

Constraints imposed on the migration. The schema was to remain byte-for-byte identical — an ORM swap, not a redesign. All business logic, including tenant scoping, capability gates, approval-stage gates and audit logging, was to be preserved with only query syntax changing. Every verification step was required to test over the same network path the real system uses.

Consequence accepted. Prisma's query engine adds a runtime dependency and its generated client must be produced during the container build; both were absorbed into the Dockerfile. Drizzle's thinner abstraction and closer-to-SQL query surface were given up.

On the verification constraint in DEC-002

The requirement that every verification step test over the real network path was not a general principle but a response to a specific failure earlier the same day. A database password rotation had been verified by connecting to PostgreSQL from inside its own container, which passed — because local socket connections in that image use trust authentication and bypass password checks entirely. The real failure only appeared over the Docker network, after the change was live. Recording the incident alongside the decision is what stops the lesson being lost with the people who were present.

DEC-003  ·  PostgreSQL as the database

Decision. PostgreSQL 15, self-hosted in a container with a scheduled backup sidecar.

Rejected. MongoDB, on the grounds that production tracking is inherently relational — a shot belongs to a sequence, belongs to an episode, belongs to a project, and integrity across those relationships is the product. MySQL was a viable alternative rejected on feature depth.

Consequence accepted. Operating a database is the studio's responsibility rather than a vendor's. Mitigated by NFR-AVL-004 and the backup service.

DEC-004  ·  Redis as cache only, explicitly not durable

Decision. Redis serves the authorisation cache, rate-limit counters and presence throttling. Persistence is deliberately disabled.

Rejected. Using Redis as a session store, which would have made session validity depend on cache durability.

Criteria. Cache loss must degrade performance, never correctness (NFR-AVL-006).

Consequence accepted. A restart empties the cache and the next requests fall through to the database. Verified in practice: an active session survives a full Redis restart, because validity derives from the signed token and the database, with Redis holding only a short-lived copy.

DEC-005  ·  Argon2id for password hashing

Decision. Argon2id.

Rejected. bcrypt, the common default, which is not memory-hard and is therefore more tractable to GPU-accelerated attack. PBKDF2 rejected on the same grounds.

Consequence accepted. Higher CPU and memory cost per authentication, which is the intended property.

DEC-006  ·  Versioned JWT sessions rather than a server-side session store

Decision. A signed token in an HTTP-only cookie carrying a version number, checked against the user's current version on every request.

Problem being solved. A plain stateless token cannot be revoked before expiry, so a logout, password change or offboarding left a valid token usable for its full lifetime. The version field restores revocation without giving up statelessness.

Consequence accepted. One validity lookup per request, mitigated by the cache in DEC-004, which fails closed (NFR-SEC-003).

DEC-007  ·  Capability-based authorisation rather than role checks

Decision. Permissions are named capabilities granted to roles in the database and checked per request.

Rejected. Hard-coded role comparisons in route handlers, which cannot be changed without a deployment and drift silently from what the interface displays.

Consequence accepted. An additional indirection between role and permission, and a matrix that must be administered. This is what makes BR-011 enforceable rather than conventional.

DEC-008  ·  Docker Compose rather than Kubernetes

Decision. Five containers on a single host: reverse proxy, API, database, cache, backup.

Rejected. Kubernetes, whose operational complexity is not justified for a single-studio deployment and which would require expertise the studio does not have.

Consequence accepted. No automatic horizontal scaling or multi-node failover. Acceptable at present scale and revisitable if a deployment outgrows one host.

DEC-009  ·  Vite and React rather than Next.js

Decision. A client-rendered single-page application built with Vite.

Rejected. Next.js, whose principal advantages are server-side rendering and search engine optimisation. Neither applies to an authenticated internal tool, and its server runtime would have added a second deployable component.

Consequence accepted. A larger initial bundle and no server rendering. Irrelevant on a studio local network.

DEC-010  ·  Turborepo for build orchestration

Decision. Turborepo over the pnpm workspace.

Criteria. Cached, parallel task execution, and attribution of a failure to a specific workspace package.

Measured outcome. A full workspace typecheck fell from approximately 17 seconds cold to 63 milliseconds fully cached, and an introduced type error was correctly isolated to the affected package while the others remained cached.

DEC-011  ·  Radix UI primitives rather than a component library

Decision. Unstyled accessible primitives, styled in-house with Tailwind.

Rejected. Material UI and Ant Design, both of which impose a visual identity that would have to be fought to achieve a studio-tool aesthetic, and both of which are heavier.

Consequence accepted. More styling work up front, in exchange for keyboard and screen-reader behaviour that would otherwise have to be built by hand (NFR-USE-006).
