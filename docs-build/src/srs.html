1  Introduction

1.1 Purpose

This document specifies the software requirements for Forge, a production tracking and review platform for animation and visual effects production. It is the engineering document of record: it defines what the software shall do in terms precise enough to design against, test against, and audit.

Its intended readers are the engineering team implementing and maintaining the system, quality assurance staff deriving test cases, and any party auditing the system's behaviour against its stated requirements.

1.2 Scope

Forge is a self-hosted web application that manages the production of visual content from initial tracking through departmental work, internal review and approval, to external client delivery. It replaces spreadsheet-based shot tracking and unstructured review feedback with a single system of record.

The software covers: identity and access management; the production hierarchy of projects, episodes, sequences, shots and assets; a tracking grid with spreadsheet import; task creation, assignment and progression; version management and media upload; a frame-accurate review player with annotation; a multi-stage approval chain; external client review by access link; attendance and effort recording; and studio administration with audit.

The software explicitly does not cover content creation application integration, render farm submission, media transcoding, financial ledger integration, or cross-tenant federation. These exclusions are recorded with rationale in SYM-FRG-REQ-001 Table 4.2.

2  Overall description

2.1 Product perspective

Forge is a self-contained system, not a component of a larger product. It replaces a manual process rather than an existing system. It comprises a browser-delivered client application, an HTTP application programming interface, a relational database, an in-memory cache, and a reverse proxy, deployed together as containers on a single host controlled by the studio.

2.2 Product functions

At summary level the software shall provide: authentication and account lifecycle management; capability-based authorisation with scoped visibility; management of the production hierarchy; a filterable tracking grid with spreadsheet import and export; task lifecycle management; version and media management; frame-accurate review with annotation; a multi-stage approval chain; external client review; attendance and effort recording; notification and messaging; and administration with an auditable change history.

2.5 Design and implementation constraints

  • CON-1. The system shall be deployable entirely on studio-controlled hardware.
  • CON-2. Core function shall not depend on outbound internet access, prohibiting runtime reliance on external content delivery networks or third-party APIs.
  • CON-3. All studio traffic may present a single network source address; protective controls shall not treat the studio as one abusive client.
  • CON-4. The system holds live production data; schema changes shall be verified against a clone restored from production before deployment.
  • CON-5. Verification of any change shall exercise the same network path as real traffic.
  • CON-6. The implementation language shall be TypeScript across all tiers.
  • CON-7. Database access shall be through the Prisma client; raw SQL is permitted only where the client cannot express the query, and shall be parameterised.

2.6 User documentation

The software shall be accompanied by SYM-FRG-USG-001, structured so that each role has a self-contained access path covering only the functionality available to that role, plus installation, configuration and troubleshooting material for the deploying administrator.

2.7 Assumptions and dependencies

Assumptions ASM-1 to ASM-6 and dependencies are specified in SYM-FRG-REQ-001 Sections 11.2 and 13, and are incorporated here by reference. The dependency of note for this specification is the SMTP relay: its unavailability shall degrade password recovery and client access-code delivery without affecting any other function.

Note on CI-005

The number of trusted proxy hops is security-relevant. Trusting more hops than exist allows a client to inject a forged forwarded-address header and defeat address-based rate limiting; trusting fewer collapses every client onto the proxy's own address. The deployment has exactly one proxy, and the configuration shall state one.

Rationale for SRS-AUTH-006c

Registration is reachable by anyone who can load the sign-in page. If the role field were honoured as submitted, that person could grant themselves studio-wide authority by choosing it from a dropdown — the most direct privilege escalation the system could offer. Separating the request from the grant keeps onboarding self-service without making authority self-service: the new starter can sign in and work immediately, and the only thing that waits on an administrator is the elevation itself.

SRS-SESS-004 is what makes a stateless token revocable. Without it, logout would clear only the browser's copy of a token that remains valid for its full seven-day life — a token captured from a shared workstation would continue to work after the user believed they had signed out.

4.8 Spreadsheet import

Priority
High
Traces to
BR-004
Actors
Production management

Description. Ingests an existing studio tracksheet without requiring the studio to reformat it. Its governing principle is tolerance: accept what is given, and never discard what is not understood.

Stimulus and response. An authorised user selects a project and supplies a workbook. The system parses each sheet, creates or reuses episodes, sequences and shots, creates a task per row, and reports the outcome of every row.

IDRequirementPri.
SRS-IMP-001The system shall accept workbooks in .xlsx, .xls and .csv formats.High
SRS-IMP-002Where a sheet name matches the pattern for an episode designation, the system shall derive the episode from the sheet name.High
SRS-IMP-003Where no sheet name matches that pattern, the system shall import any sheet containing recognisable shot rows under a default episode.High
SRS-IMP-004The system shall skip a sheet containing no recognisable shot column, and shall not create records from it.High
SRS-IMP-005Column matching shall be insensitive to case, whitespace, underscores and hyphens, and shall accept a defined set of synonyms per field.High
SRS-IMP-006The system shall preserve every non-empty column it does not map to a known field, recorded against the created task.High
SRS-IMP-007The system shall limit the parsed row range to a bounded maximum irrespective of the range the sheet declares.High
SRS-IMP-008The system shall parse both slash-separated and eight-digit day-month-year date forms, and shall record no date rather than an incorrect one where a value cannot be confidently parsed.High
SRS-IMP-009The system shall attempt to match a named artist to an existing user by whole-word comparison of all name parts.Med
SRS-IMP-010The system shall report the outcome of each row as created, updated or skipped, with a reason for each skip.High
SRS-IMP-011Where no shot row is found anywhere in the workbook, the system shall report this as a failure and shall state what was expected.High
SRS-IMP-012Import shall be idempotent with respect to shots: re-importing a workbook shall reuse existing shots rather than duplicating them.High
 Table 4.8 — Import requirements.
Rationale for SRS-IMP-007

A real production tracksheet was observed declaring a range extending to the spreadsheet format's maximum row count, because a single stray value existed at that row. Parsing the declared range materialised approximately one million mostly-empty row objects and took over thirty seconds, which presents as a hung application. The bound is a correctness requirement, not an optimisation.

Rationale for SRS-IMP-011

Reporting "0 of 0 rows imported" as a success is indistinguishable from a silent failure to the user. The system shall state that no shot column was recognised and name the headers it looks for.

Rationale for the asymmetry between SRS-SEC-008 and SRS-SEC-009

These two requirements deliberately fail in opposite directions. Rate limiting is an availability control: if its store is unavailable, denying every request would convert a cache outage into a total outage, so it fails open. Session validity is a security control: if it cannot be determined, permitting the request would allow a revoked session to continue, so it fails closed. Stating both explicitly prevents a future maintainer from "correcting" one to match the other.

7.1 Verification constraints

VER-CON-1 — Verification shall traverse the real path

Any verification of a deployed behaviour shall exercise the same network path, authentication mechanism and configuration as production traffic. Verification through a privileged local channel that bypasses a control under test shall not be accepted as evidence.

Basis. A database credential rotation was previously verified by connecting from within the database container, which succeeded because local socket connections in that image use trust authentication and bypass password verification entirely. The real failure appeared only over the network, after the change was live. The constraint exists so this class of false-positive cannot recur.

VER-CON-2 — Schema changes shall be verified against real data

Any migration or data-layer change shall be executed against a clone restored from a production backup before being applied to the live system, and the restored clone shall be confirmed non-empty before it is used as evidence.
